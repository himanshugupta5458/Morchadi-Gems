# Buttons render as thin labels with the text hugging the top and bottom edges

- **Date:** 2026-08-18
- **Prompt:** 24
- **Severity:** Major
- **Status:** Resolved

## Symptom

The primary and secondary buttons had almost no vertical height. The label sat flush against
the top and bottom borders, so they read as outlined text rather than as buttons. The hero's
two CTAs were the clearest case.

Three prompts had already changed the padding:

| Prompt | Change | Reported as |
| --- | --- | --- |
| 22 ([ADR-023](../decisions/ADR-023-home-polish.md)) | `px-7 py-3.5` → `px-10 py-4` | shipped |
| 23 ([ADR-024](../decisions/ADR-024-funnel-ui-polish.md)) | `px-10 py-4` → `px-12 py-[1.375rem]` | shipped, "a 64px button" |
| 24 | reported by the user as still wrong | — |

Each of those prompts verified the new class string in the rendered HTML and found it. The
buttons did not change.

## Investigation

**Ruled out first: the class not reaching the element.** It did.
`.next/server/app/index.html` carried `px-12 py-[1.375rem] text-label` on both hero CTAs. This
is the check the two previous prompts ran, and it is why they concluded the change had landed.

**Ruled out: a call site overriding the padding.** `Button` declares its props as
`Omit<ButtonHTMLAttributes<HTMLButtonElement>, "className">` and `ButtonLink` has no
`className` prop, so an override is a type error. All 44 call sites confirmed clean.

**Ruled out: a fixed height or a short line box capping it.** No `h-*`, `min-h-*`, `max-h-*`
or `leading-*` anywhere in `buttonClasses()`.

**Found it: grep the emitted stylesheet rather than the markup.**

```
$ grep -oF '.py-\[1\.375rem\]{' .next/static/css/*.css
(no output)
$ grep -oF '.px-12{' .next/static/css/*.css
(no output)
```

The class was on the element. The rule did not exist. With no `padding` declaration
resolving, the button's height was its 18px line box plus its 1px borders — about 20px, not
64px.

Checking the rest of the button's classes against the same bundle showed the pattern:

| Class | In the bundle |
| --- | --- |
| `py-[1.375rem]` | absent |
| `px-12` | absent |
| `text-[0.6875rem]` | absent |
| `leading-4` | absent |
| `py-4` | present |
| `py-2.5`, `px-5`, `py-3` | present |

Every present one is a utility some file under `app/` or `components/` also uses. Every absent
one is unique to `lib/button-styles.ts`.

## Root cause

`tailwind.config.ts` scanned `./pages`, `./components` and `./app`. It did not scan `./lib`.

`lib/button-styles.ts` is the only file in the repository that declares Tailwind classes
outside a component, which is deliberate — [ADR-004](../decisions/ADR-004-design-system.md)
put them there so `Button` and `ButtonLink` could not drift apart. Tailwind never read the
file, so it never generated rules for the class names in it.

The bug was partially masked because a utility landed in the bundle anyway whenever some
scanned file happened to use the same one. `py-4` from prompt 22 was generated by coincidence,
which is why the buttons had *some* padding and the problem read as "not enough" rather than
"none". Prompt 23 replaced it with an arbitrary value used nowhere else, which removed the
coincidence and took the padding to zero.

## Fix

`tailwind.config.ts` — added `"./lib/**/*.{js,ts,jsx,tsx,mdx}"` to `content`.

`lib/button-styles.ts` — padding set in plain scale values rather than arbitrary ones:

```
md: "px-8 py-5 text-label"            60px tall
sm: "px-5 py-2.5 text-[0.6875rem]"    ~38px tall
```

`lib/button-styles.test.ts` — the two padding assertions updated, plus a new case asserting
no `h-*`, `min-h-*`, `max-h-*` or `leading-*` appears in either size, so padding remains the
only thing that decides the height.

## Verification

Against the emitted stylesheet, not the markup:

```
$ grep -oE '\.(px-8|py-5|px-5|py-2\\\.5)\{[^}]*\}' .next/static/css/*.css
.px-8{padding-left:2rem;padding-right:2rem}
.py-5{padding-top:1.25rem;padding-bottom:1.25rem}
.px-5{padding-left:1.25rem;padding-right:1.25rem}
.py-2\.5{padding-top:.625rem;padding-bottom:.625rem}
```

`text-[0.6875rem]` now resolves too (`font-size:.6875rem`), so the card button's type is
actually 11px for the first time.

Rendered classes on the hero CTAs are `px-8 py-5 text-label`; on card buttons,
`px-5 py-2.5 text-[0.6875rem] w-full`. Gate: typecheck, lint, 481 tests across 19 files, and a
cleared-cache 68-page build, all green.

## Prevention

**The content glob.** Any future file under `lib/` now works. `config/` and `types/` remain
unscanned and are currently class-free.

**Ordinary scale values over arbitrary ones in the shared button.** An arbitrary value only
exists if the file declaring it is scanned, so it is the value most likely to disappear
silently. Recorded in [ADR-025](../decisions/ADR-025-button-padding-tailwind-content.md).

**A changed verification habit, which is the real lesson.** "The class is in the HTML" is not
evidence that a style applied. It passed three times here while the rule was absent. Grep the
emitted CSS for the declaration.
